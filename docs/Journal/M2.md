# M2 — Double hashing

**Date:** 2026-07-17 · **Branch:** feat/bloom-filter-core · **Base SHA:** 281c0e6

## Goal
Derive the `k` bit positions for an item from a single hash, using double hashing
(Kirsch–Mitzenmacher) so we avoid computing `k` independent hashes while keeping a
well-distributed position sequence.

## What was done
- Added `internal/bloom/hash.go`:
  - `hashParts(item) (h1, h2)` — two 64-bit halves from an xxhash digest.
  - `ensureNonZero(x)` helper — maps `0 → 1` to avoid a degenerate step.
  - `positions(h1, h2, m, k) []uint64` — `g_i = (h1 + i·h2) mod m` for `i = 0..k-1`; returns `k` positions, each `< m`.
- Table-driven tests in `hash_test.go` (100% coverage), matching the sizing-test pattern.

## Decisions & why
- **Double hashing over k independent hashes** — Kirsch–Mitzenmacher shows two hashes give the same false-positive performance as `k` at O(1) hashing cost. Recorded in ADR-0004.
- **`ensureNonZero` guard on `h2`** — if `h2 == 0`, every `g_i` collapses to `h1`, producing one repeated position and inflating the true FPP. Forcing `h2 = 1` keeps the sequence non-degenerate. Extracted as a named helper (not an inline branch) so the intent is self-documenting and independently testable.
- **`k <= 0` guard** — returns an empty slice rather than looping on a bad count; defends the position loop against a misuse that sizing should never produce but the API shouldn't trust.

## Verification
- `go test ./internal/bloom/` — green, 100% coverage on `hash.go`.
- Tests assert: exactly `k` positions returned, every position `< m`, and the `h2 == 0` case stays non-degenerate.
