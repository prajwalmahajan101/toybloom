# M1 — Sizing math

**Date:** 2026-07-16 · **Branch:** feat/bloom-filter-core · **Base SHA:** 77f5611

## Goal
Implement the pure sizing math for the Scalable Bloom Filter: derive the bit-array
size `m` and hash-function count `k` from `n` and `p`, plus the per-stage error
budget and capacity used to chain stages. No storage, no HTTP — logic only.

## What was done
- Added `internal/bloom/sizing.go` with four functions:
  - `OptimalM(n, p) (uint64, error)` — `m = ceil(-n·ln(p)/ln2²)`.
  - `OptimalK(n, m) (int, error)` — `k = max(1, round((m/n)·ln2))`.
  - `StageError(p, i, r...) (float64, error)` — stage-`i` budget `p₀·r^i`, `r` optional (defaults `DefaultR = 0.9`).
  - `StageCapacity(n, i, s...) (uint64, error)` — stage-`i` capacity `n·s^i`, `s` optional (defaults `DefaultS = 2`).
- Precomputed `ln2` / `ln2²` constants; sentinel errors for invalid `n`/`p`/`r`/`s`.
- `optionalRatio` helper resolves the variadic override against a default (0 or 1 value; >1 is programmer misuse).
- Exhaustive table-driven tests in `sizing_test.go` (100% coverage), matching the LLD self-check table.

## Decisions & why
- **Optional `r`/`s` via variadics** — keeps the common call site clean (defaults `0.9`/`2` per LLD) while allowing per-stage overrides without a config struct. Directly answers the RFC open question "do we need configurable r/s?".
- **Explicit `math.IsNaN()` validation guards** — replaced an earlier inverted-boolean form (`!(p > 0 && p < 1)`) that mishandled NaN, which also cleared SonarQube **S1940**. NaN inputs now fail loudly with a sentinel error instead of slipping through.
- **Functions return `(_, error)` rather than panicking** — invalid sizing inputs are a caller error, surfaced explicitly per the project's no-silent-failure rule.
